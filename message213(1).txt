Hi all, I will summarize the situation regarding the plain implementations:

Fields: The implementations for bn254 and bls12-381 are imported from Arkworks. The implementations for Goldilocks, Koalabear, Babybear, and Mersenne31 are imported from Plonky2/3 (I feel this part of the implementation in Plonky2/3 is highly optimized). I removed felt252 because I feel this field is rarely used. Most of the original implementation code was adapted from public repositories. I replaced the underlying field calls with ours (as described above) to ensure a fair comparison. The security parameter is set to 128 bits. I feel that different hashes have different focuses; for instance, Monolith focuses on small fields around 32-bit, while Tip5, Tip4, and Tip4' focus on Goldilocks. Therefore, some hashes should arguably only be compared on specific fields and state widths.

State width: Denoted by "t". I only considered state widths corresponding to approximately 512 bits and 768 bits.

zkfriendlyhashzoo: https://extgit.isec.tugraz.at/krypto/zkfriendlyhashzoo/-/tree/master

Remaining issues:
1. For hashes that deploy matrices that only require the MDS property , such as Anemoi, Poseidon, and Neptune, the matrix multiplication calculation can exploit the matrix structure (e.g., using a circulant matrix allows for NTT optimizations or viewing it as a convolution to exploit efficient convolution algorithms). The current implementation simply selects a Cauchy matrix and uses an O(t^2) algorithm(except monolith). Regarding this part, there are two points of concern. First, some public implementations use O(n log n) algorithms (e.g., Monolith). Should we unify these matrices (e.g., ensure different hashes use the same matrix and multiplication method)? This seems like the fairest approach. Second, for small t, the trivial algorithm seems better. The O(n log n) algorithm might only become superior when the state width is larger (I am unsure where the critical threshold lies).
2. Other configurations that need to be added, especially for the last 7 hashes
3. Currently, there is still no implementation over binary fields (even characteristic can use the bench from Poseidon(b), but odd characteristic hasn't been organized yet). Also there is no Arion implementation.
4. In the current benchmark, Keccak-256 and SHA-256 are measured as full hash functions, not as single permutations like the other benchmarks. So comparing them under the same “per-permutation” metric is not very appropriate. I guess we should instead estimate an equivalent number of permutations based on the input data size.
